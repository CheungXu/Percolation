# Percolation 个人碎片记忆系统架构规划与实施路线图

## 1. 项目背景与目标

日常生活中，用户习惯通过即时通讯工具将零碎灵感、临时事项、购物比价、个人缩写或半截短句随手发给自己作为备忘。这种记录方式在输入端几乎没有阻力，但随着时间推移会产生两个突出痛点：

1. **历史积压难寻**：消息流不断增长，早期记录被淹没在海量流水中。
2. **表达残缺与提问模糊的断层**：记录时往往是只有本人能懂的极简短语或个人暗语，而数月后回想时只能提出非常模糊的印象式问题，传统关键词搜索和单纯的相似文本匹配难以准确召回。

**Percolation** 旨在构建一套“零输入负担、后台自动成体系、支持极度模糊召回、且面向未来 C 端多用户平滑扩展”的智能体记忆系统。

## 2. 已确认的产品边界与关键技术决策

### 2.1 第一版（MVP）范围

- **暂不接入外部聊天工具采集端**：第一版聚焦记忆存储、后台整理与混合检索内核，通过标准接口录入与查询，确保核心记忆闭环跑通。
- **默认单用户运行，底层预留多用户隔离**：第一版面向个人自用验证效果，但所有数据存储、文件路径与安全执行边界从第一天起按多租户标准设计，避免未来产品化时推倒重写。

### 2.2 已拍板的三项核心选型

1. **智能体运行内核**：采用 **Python 零框架自研轻量循环**。直接复用团队在相邻项目中已验证成熟的国产多模型接入与后端基建，吸收业界极简工具集（降低单次调用开销）与“轻量路由裁判 + 独立目录执行器”的分层思想，避免第三方重型框架的黑盒损耗与频繁升级风险。
2. **跨机器共享存储底座**：采用 **阿里云通用型文件存储（NAS，广州同地域、容量型、按量付费）** 承载用户的结构化记忆文档（核心注入文件、候选缓存目录、主题知识库页面）。本机是轻量应用服务器，需经内网互通接入一块网段不重叠的专有网络后再挂载。多台计算节点可同时挂载，后续云端沙箱也可按用户目录动态挂载。
3. **命令执行安全隔离**：采用 **两阶段平滑演进策略**。当检索需要探查候选缓存目录时，第一版在本机通过轻量级系统内核沙箱将可见范围严格限制在当前用户的专属只读子目录内；未来面向海量 C 端用户扩容时，无缝切换至阿里云云端沙箱服务并动态挂载对应用户的存储子目录。

## 3. 四层记忆总体架构

系统借鉴人类大脑“实时捕获经历 + 睡眠期离线整合”的分工机制，将记忆划分为由底向上的四个层级：

```text
L4 运行注入区（热区：MEMORY.md）
   └── 每次会话固定加载，严格控制篇幅；仅存放已确认的核心背景与高频个人暗语

L3 候选缓存区（温区：MEMORY_CACHE/ 多文件目录）
   └── 存放固定但不常用的背景、低频暗语与历史设定；默认不加载，仅在首轮检索未命中时按需探查

L2 网状知识导航层（主题知识库：wiki/ 互链页面 + 数据库混合索引）
   └── 按主题高内聚聚合碎片信息，补充上位概念词与页面间关联，充当缩小检索范围的导航地图，并强绑定原始记录编号

L1 原始事实与反馈层（关系型数据库：阿里云 RDS PostgreSQL 独立库）
   └── 不可篡改地保存用户原始录入语句、时间戳、连发批次，以及每次检索的命中与兜底统计
```

## 4. 核心业务流转机制

### 4.1 录入与离线整理链路（自底向上：Dreaming）

1. **无感极速录入**：用户随手发送的零碎信息直接写入底层数据库并标记为“待整理”，不做实时追问或分类打断。
2. **后台定时唤醒**：系统在夜间空闲时段（可利用大模型夜间低峰算力优惠）唤醒后台整理任务，仅针对近期有新消息或缓存命中变化的用户执行自底向上的演进：
   - **上下文拼图与归档（L1 → L2）**：结合核心背景与前后连发消息，还原半截话语境，更新或合并至对应的主题知识页，同时保留原始消息锚点防止信息失真；对无把握的猜测做明确标记，不混同于已确认事实。
   - **热度升降级置换（L2 ↔ L3 ↔ L4）**：结合一段时期内的检索反馈记录，将候选缓存区中被频繁触发命中的词条自动晋升至运行注入区；当运行注入区接近篇幅上限时，将长期未使用的低频条目下沉回候选缓存区，根据累积程度自动决定局部微调或周期性全局重整。

### 4.2 在线混合检索链路（自顶向下 + 兜底穿透）

1. **主路径检索**：系统加载运行注入区核心记忆与检索技能，理解用户模糊意图；若意图明确，依次通过“网状主题导航层（结合中文分词、语义向量与关联邻居页面） + 近期尚未归档的新增原始记录”定位信息，并回溯原始语句核验后作答。
2. **候选缓存区静默兜底**：若首轮遇到未知个人暗语或主路径未能召回有效结果，系统先不打扰用户，自动在受限沙箱内探查候选缓存区目录寻找线索；一旦找到映射关系，自动改写检索词重新执行一轮查找，并记录本次缓存命中供后续后台整理参考。
3. **最小化追问与闭环**：仅当穿透候选缓存区后仍存在无法消解的歧义或确实无记录时，才向用户发起简短追问或如实告知未找到；用户的澄清回复将作为高优事实入库，确保同类暗语不再重复询问。

## 5. 云基础设施复用与多用户扩展准备

- **计算与调度**：初期与现有服务共用这台广州轻量应用服务器（规格 4 vCPU / 16 GiB，实例名 Ubuntu-clhn）。检索接口以常驻服务运行，夜间整理用系统定时器触发，建议落在 03:00–04:00。
- **数据库底座**：已在现有广州 PostgreSQL 上新建独立库，和相邻业务的库分开。运行账号看不见其他用户的数据；不声明当前用户时，一行也看不见。原文录入时不算向量，向量只跟已整理的主题页走。中文检索用库内重叠二字，因为词典分词插件要重启整台数据库，而这台数据库还承载相邻业务。
- **共享文件底座**：广州通用型 NAS 已挂到本机 `/mnt/percolation`。这台机器是轻量应用服务器，网络在阿里云托管的专有网络里，和账号里原有的默认专有网络网段重叠，因此另建了不重叠的专有网络 `percolation`（`10.0.0.0/16`），用内网互通把轻量服务器接进去后再挂载。按量计费，目前几乎无存量。后续按用户标识在这个根路径下划分工作空间。
- **多模型协同**：复用已打通的阿里云百炼与火山方舟通道。文本向量和重排已实测可调用：向量为 1024 维，重排能把「显示器」排到支架那条记录上。在线检索优先用响应快的模型，夜间整理用推理更强的模型。

### 7.4 检索与整理（下午更新）

- 智能体内核和业务分开：通用部分以后建别的智能体时直接用，本项目只写自己的工具、提示词和流程。
- 检索分四步：先读热区理解提问；再查主题页和近期原话，回到原话核对后作答；答不上时先在候选区里静默找线索，改写后重查；仍不行才简短追问或如实说没找到。
- 夜间整理：只处理有新消息或候选区被用到的用户；把原话按连发批次归入主题页，同步索引；候选区里两周内帮上忙两次以上的已确认条目晋升进热区，热区偏满时把冷条目下沉回去。每次整理都留版本快照，失败就整体退回。
- 真机验收用临时测试用户跑了四个场景，21 项全部通过，测试数据已清理：
  - 刚录入、还没整理的记录能直接查到。
  - 整理后生成了带原话锚点的主题页，索引和版本快照都在。
  - 一个只记在候选区的个人暗语，前两次靠静默穿透答对；整理后自动晋升进热区，第三次直接命中。
  - 未知指代会追问，用户回答后能答对，并被固化进候选区；热区不含推测；用户之间互相看不见。
- 当前耗时：普通提问约 9 秒；需要穿透候选区的约 20 秒；暗语晋升进热区后同类提问约 7 秒。
