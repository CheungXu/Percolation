# 执行环境追溯与复现：落地记录

日期：2026-11-13

## 背景

可观测性上线后，每次检索和整理都有完整轨迹，能看清“模型看到了什么、做了什么”。但要真正复现一次运行，还缺“它当时站在什么环境上”：用户工作区是哪个版本、库里有哪些原话和检索记录、当时几点、跑的是哪版代码和配置。另外，原先整理是一边改文件一边刷新索引，同一时刻的检索可能读到“新文件 + 旧索引”的半成品，环境本身就不是一个确定的东西。

本次在不升级向量与重排模型的前提下，把这两件事一起解决。

## 做了什么

| 方面 | 结果 |
| --- | --- |
| 环境一致性 | 夜间整理改为在独立暂存区里写，收尾时用一个数据库事务统一发布索引、原话状态和“已发布版本号”，之后主工作区再前移。检索全程只看到已发布版本。失败时直接丢弃暂存区，不再需要回滚补偿。 |
| 环境记录 | 每次检索、整理开跑前，把工作区版本、数据库水位（时刻、原话序号、待整理集合、检索记录数）、代码/依赖/配置指纹、整理模式及理由记进轨迹。 |
| 时钟固定 | “当前日期”、晋升统计窗口、重整间隔等所有时间判断改用记录下来的时刻，复现时注入原值。 |
| 一键复现 | `trace_cli.py reproduce <轨迹号>`：自动建临时“回放租户”，还原工作区版本和数据库水位，按原入参重跑 N 次，输出逐项对比与稳定性报告，结束后清理。回放运行会拦截有外部副作用的工具。 |
| 轨迹清理 | `trace_cli.py purge --tenant`：按租户删轨迹并回收不再被引用的大文本；统计与列表默认不计回放轨迹。 |
| 数据库 | 新增迁移 004（`users.workspace_head`），已执行，存量 2 个用户已回填。 |

## 验收

- 单元测试 38/38（原 31 项 + 新增 7 项：时钟注入、模式判定、维度分布、回放拦截、轨迹清理与回收、环境摘要、暂存整理的失败隔离/发布/等价/锁/人工改动发布/中断修复）。
- 真机端到端 38/38（原 27 项 + 新增 11 项），用时约 13 分钟，其中：
  - 整理进行中发起检索：主工作区未变、检索记录的版本与已发布版本一致；整理完成后主工作区与库中版本号一致。
  - 人为让发布事务失败：主工作区、六张派生表、原话状态全部保持原样，暂存区已清空。
  - 复现候选区兜底检索、维度检索、一次整理，各重跑 2 次：水位与原记录完全一致、代码与配置无差异；两次检索都复现了原结果与原路由；两次整理的模式、归档集合与原运行一致；回放租户全部清理，6 条回放轨迹带标记保留。
- 一个观察：整理重跑时页面数、切片数、事件数和改动的文件集合都与原运行一致，但页面维度标签多了 1 个（14→15），其中一次重跑少写了 1 条页面链接（2→1）。这是模型输出本身的随机性，报告会如实列出，不算复现失败。

## 上线后自查修复（同日）

代码自查发现 5 个问题，逐一核实后都属实，已修复：

| 问题 | 影响 | 处理 |
| --- | --- | --- |
| 人工在工作区提交过之后，整理开头误判为“版本分叉”直接报错 | 该用户之后的整理和 reindex 全部卡死（已用临时仓库复现） | 区分“落后/领先/分叉”三种情况：落后补齐，领先重新发布，只有真正分叉才要人工处理 |
| 数据已发布、主工作区还没跟上时若出异常，暂存分支会被删 | 新版本的文件只靠 git 的临时保留（约两周）存在，过期后无法补齐 | 数据一发布就保留分支，主工作区跟上后才删；补齐后自动清理残留分支 |
| 主工作区跟进失败时，整理结果仍显示成功、无提示；补齐只能等下一次整理 | 运维看不到问题；期间检索读到旧文件 | 结果里写明“已保留分支”；检索发现落后时，若此刻没有整理在跑，会先补齐再检索 |
| 复现时临时租户建到一半失败不会被删除 | 残留临时租户和工作区 | 先登记再创建，失败也会清理 |
| 原运行时工作区有未提交改动，复现报告不提示；git 卡住时检索可能跟着卡住 | 复现差异容易被误判为模型不稳定；在线请求可能卡住 | 复现报告开头给出警告；git 调用统一 60 秒超时，检查失败只记“未知”、不影响检索 |

修复后单元测试 40/40（新增版本比对三种情况、复现警告两项，并在数据库用例里覆盖检索侧补齐与整理进行中跳过）。

## 二次复核与按需处理（同日）

对全部 7 个复查点逐一核实后，区分“立即修复”与“现阶段无需修改”处理如下：

| 复查项 | 核实结论 | 决策与处理 |
| --- | --- | --- |
| 主工作区落后且存在同文件未提交改动时补齐失败，且异常丢失 Git 具体报错 | **属实**：不重叠改动可直接快进，同文件冲突会被拒绝，而标准异常不含冲突文件名 | **已修复**：透传 Git 错误详情，保留人工现场不覆盖、不制造分叉，并在报错中直接给出暂存恢复命令 |
| 复现整理时传入了原判定结果而非原请求参数，绕过了模式重算 | **属实**：导致自动判定逻辑在复现时未真正重跑 | **已修复**：改为传原始请求参数重跑自动判定，并把判定理由纳入复现对比与稳定性统计 |
| 检索日志按时间水位复制的并发边界 | **部分需修**：事务起点时间在极窄间隙下会早于刚提交的日志；未提交写事务窗口（<2ms）在个人库概率极低 | **已修复前半项**：水位时钟改取实时库时钟避免漏复制；后半项不存全量日志列表以防轨迹膨胀，继续由水位核对项监控 |
| 维护类与回放类 Git 命令仍缺超时（`gc` 持整理锁运行） | **属实** | **已修复**：补齐全部剩余 Git 调用超时（常规 60 秒、`gc`/`clone` 120 秒），维护/清理超时不阻塞主流程 |
| 跨天复用的旧大文本在并发落盘瞬间可能被清理误删 | **属实**：命中已有文件未刷新修改时间，不享受宽限期保护 | **已修复**：命中已有文件时刷新修改时间进入宽限期保护，遇并发删除自动重写 |
| 线上工具暂未打外部副作用标签 | **属实但非缺陷**：当前工具均为读库或隔离工作区读写，无外部写操作 | **无需修改**：保留框架拦截能力供后续接入外部通知/写接口时使用 |
| 代码环境指纹按进程缓存 | **属实但符合运行语义**：不重启进程时内存运行的就是启动时的代码与提示词 | **无需修改**：保留进程级缓存，既避免每次请求跑子进程，又真实反映内存运行版本 |

二次修复后单元测试 41/41 通过。

## 检索原话命中呈现与外部修改发布优化（补充）

1. `retriever.py`：原话命中呈现增加录入时间与所属星期（例：`· 录入 2026-11-13(周五)`），便于追溯与核验；日期兜底过滤说明文案优化，避免误解。
2. `search.py`：`SearchOutcome.as_dict()` 对 `date_range` 序列化为列表，保持与外层类型一致。
3. `dream.py`：`prepare_workspace` 先计算计划再提交外部修改，发布失败自动执行 mixed reset 撤回提交，消除 HEAD 领先而库未推进的半截状态；`repair_fast_forward` 补齐前清理陈旧锁。
4. `memory_fs.py`：新增 `git_reset_mixed` 支持安全的本地事务撤回。

## 使用方式（给运维/研发）

- 查某次运行的环境摘要：`trace_cli.py show <轨迹号>`。
- 复现：`trace_cli.py reproduce <轨迹号> --runs 3`；只能复现本次上线之后产生的轨迹。
- 人工改了用户工作区文件后，要执行 `percolation_cli.py reindex` 发布，否则检索读到的是未提交文件，日后复现只能拿到上一次提交。

## 遗留与后续建议

1. 本次上线前的历史轨迹没有环境记录，无法复现。
2. 若当时代码与现在不同，报告会给出用旧代码复现的命令，但不会自动切换代码版本。
3. 外部模型服务自身的版本变化无法冻结，只能通过指纹和模型名追踪。
4. 定时整理（systemd）仍未启用，启用前建议先在真实用户上跑一次 `reproduce` 观察稳定性。
5. 测试与回放产生的轨迹目前保留，可按需用 `purge` 定期清理。
