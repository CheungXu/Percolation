# Agent 跨会话记忆架构与执行内核（Harness）设计指南

本文提炼自 Anthropic《The components of agent memory》、Letta Context Repositories、PI Agent 以及 DeepSeek Harness / SuperAgent 的工程实践，总结构建高可靠、低成本、支持多租户扩展的 Agent 记忆与执行底座的通用准则。

---

## 一、 Agent 记忆系统的五大核心设计准则

### 1. 在线捕获与离线整理（Dreaming）读写分离
- **痛点**：Agent 在线执行主任务或接收碎片输入时，既难以预判未来真正需要什么，又容易因频繁整理文件而分散注意力、拖慢响应。
- **做法**：
  - **在线阶段尽量轻**：优先保证原始交互/输入（Raw Transcripts）无损落库；仅对极其明确的关键结论做轻量记录。
  - **离线阶段深度重整（Sleep-time Compute / Dreaming）**：利用空闲时段算力回看原始日志，跨多轮输入补全上下文、合并重复主题、构建网状索引。

### 2. 原始记录是唯一事实基准（Ground Truth），严防摘要失真
- AI 对原文做多轮概括极易丢失关键限定条件，甚至将早期错误判断固化为后续会话盲目信任的“铁律”。
- **铁律**：
  1. 底层原始记录表只追加、不篡改；
  2. 中上层知识库（如主题 Wiki）的每条结论必须附带指向底层原始记录的锚点 ID，检索回答时回溯原文核验；
  3. 严格区分 **`[已确认事实]`** 与 **`[待验证推测]`**，未经印证的推测严禁上浮进入顶层全局注入上下文。

### 3. 保持高内聚主题页，警惕“碎片爆炸”与“1:1 地图陷阱”
- **防碎片爆炸**：切忌每条事件/消息生成一个独立小文件（会导致文件数失控且历史过期状态难以清理），应围绕长期主题或领域维护少量高内聚文档，动态覆写最新状态。
- **防过度扩写**：知识库的作用是充当“缩小检索范围的导航地图”与“跨文档概念桥梁”，如果写得比原始材料还冗长，就丧失了抽象价值。

### 4. 顶层预注入必须克制，引入 L1/L2 缓存热度置换机制
- 每次会话启动时预注入的顶层记忆（如 `MEMORY.md`）能解决“不知道该搜什么”的冷启动盲区，但过长的指令文件会同时推高 Token 成本并降低模型指令遵循度（通常建议控制在 200 行以内）。
- **热温分层方案**：
  - **热区（运行注入区）**：仅保留核心背景与高频个人暗语，随每次请求默认注入。
  - **温区（候选缓存区）**：存放固定但低频的知识。首轮未命中或遇到未知指代时，由 Agent 按需探查兜底；探查完成前不要向用户追问。温区不维护总目录，执行器直接列目录、搜索文件来发现条目。遥测命中日志由离线 Dreaming 用来把高频条目晋升入热区，把长期未用的热区条目下沉回温区。

### 5. “网状文档导航 + 混合检索”优于纯三元组图数据库
- 对于口语化、带条件语境与状态演进的信息，强拆为 `(实体)-[关系]->(实体)` 三元组容易丢失语境且增加模型查询难度。
- 更优实践是**“文件即本体，数据库即索引”**：本体采用带双向链接与别名元数据的 Markdown Wiki（大模型读写最自然），每次文件更新后由确定性程序自动同步生成“中文分词全文索引 + 向量语义索引 + 链接关系边表”，兼顾可读性与多跳混合召回精度。

## 二、 自研轻量 Agent 执行内核（Harness）选型与构建经验

### 1. 看清框架光谱：别为简单清晰的循环交“固定 Token 税”
- 重型全功能 Coding Agent 整机往往内置数万 Token 的通用系统提示词与数十个工具定义；在高频短任务或 C 端产品中，每次请求都会产生数倍的固定输入 Token 损耗。
- 当业务控制流清晰可控时，**官方模型客户端 + 200 行以内的白盒工具循环 + 强类型结构化输出校验**往往比引入复杂框架更省成本、更易调试，且彻底规避第三方预览版框架频繁破坏性更新的风险。

### 2. 吸收标杆项目的三大架构精髓
1. **向 PI Agent 学“极致减法与缓存友好”**：核心只暴露最正交的 4～5 个原子工具（如受限 `read` / `write` / `edit` / `bash` / `hybrid_search`）；技能（`SKILL.md`）在初始上下文仅展示单行名称与适用简述，命中后再按需读取正文，最大化保持系统提示词前缀稳定以命中大模型 KV Cache。
2. **向 DeepSeek SuperAgent 学“智力拆分（Router vs. Worker）与单库事务”**：
   - 将“占用最少人类注意力”作为交互准则：主控路由层保持极简、无破坏性写权限，专注意图判断与最小化追问；繁重的文件探查与改写交给隔离工作目录内的执行器。
   - 状态变更与待触发副作用在单一数据库事务内原子落盘，服务中断重启时依靠状态对账（Reconciliation）恢复而非脆弱的日志重放。
3. **向 Letta 学“记忆版本化与碎片重整（Defragmentation）”**：将日常小幅增量修改与低频全局碎片重整拆成两种不同节奏的后台任务，避免记忆库随时间腐化。

## 三、 云上跨机器存储与多租户安全隔离避坑清单

1. **跨机器共享 POSIX 存储选型避坑**：
   - **切勿将块存储多重挂载（EBS Multi-Attach）直接格式化为 ext4/xfs 跨机读写**：多机内核缓存不同步会导致文件系统瞬间损坏。
   - **切勿用仅支持顺序追加写的对象存储 FUSE（如默认模式下的 ossfs 2.0）承载频繁改写与重命名的知识库**。
   - **正确选型**：追求全托管零运维且需对接云函数沙箱动态挂载时，优先选同地域 **通用型 NAS**。计算节点是云服务器 ECS 时，挂载点放在它所属的专有网络里。计算节点是轻量应用服务器时，它的专有网络对用户不可见，且常常和账号默认专有网络一样同为 `172.16.0.0/12`；必须另建不重叠网段，再用内网互通接进去。操作步骤与本次踩坑见 `aliyun-swas-nas-mount.md`。`AgenticFS` 目前不在广州开服，跨城挂 NFS 的延迟和专线费用都不适合小文件知识库。按数 TB 起步硬性计费的超算并行存储（CPFS）也不适合这个体量。追求更低单价且愿意自己维护挂载守护进程时，可选 JuiceFS（对象存储 + 关系库元数据）。
2. **允许 Agent 执行 Shell 命令时的多租户红线**：
   - 应用层的路径字符串校验拦不住子进程逃逸。
   - 单机阶段必须使用操作系统内核命名空间隔离（如 Linux `bubblewrap`，检索阶段使用 `--ro-bind` 只读绑定单租户子目录、`--unshare-net` 禁网、`--clearenv` 剥离宿主机密钥）；多机规模化阶段切换至云端容器/微虚拟机沙箱按会话动态挂载单租户子目录。
3. **数据库多租户防串数据双保险**：业务表以租户键作为复合索引首列，并启用 PostgreSQL 强制行级安全（`ENABLE + FORCE RLS`）。建表账号与运行账号必须物理分开（规避云厂商高权限账号默认 `rolbypassrls = true` 导致策略静默失效），做到未注入事务级租户上下文时默认全拒。完整配置范式见 `aliyun-rds-pg-multitenant-and-hybrid-search.md`。
4. **不要为了中文分词插件重启共享实例**：`pg_jieba` 和 `zhparser` 均要求写入 `shared_preload_libraries` 并重启整台 RDS 实例。共享实例上优先采用库内 `IMMUTABLE` 中文重叠二字 `tsvector` + `pg_trgm` + `halfvec` 组合，零停机获得多级权重全文与向量混合召回（详见 `aliyun-rds-pg-multitenant-and-hybrid-search.md`）。
