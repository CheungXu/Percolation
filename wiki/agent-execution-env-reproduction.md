# Agent 执行环境追溯与复现：锚点、暂存发布与回放租户

轨迹只记录了“模型看到了什么、做了什么”。要复现一次运行，还得知道它当时站在什么环境上：工作区是哪个版本、库里有哪些数据、几点钟、跑的哪版代码和配置。这里把在 Percolation 上落地的做法抽象成通用经验，适用于“文件工作区 + 关系库 + LLM 节点”的 agent 系统。

## 1. 先保证环境本身一致，再谈记录

记录环境之前，要先确保“某一时刻的环境”是一个确定的东西。最常见的破坏者是**写到一半的状态被并发读到**：整理 agent 一边改文件、一边刷新索引，检索刚好读到新文件 + 旧索引。

做法：**暂存写入 + 单事务发布 + 快进**。

- 写入方在独立 git worktree 里干活（`staging/<租户>/<run_id>`，分支 `dream/<run_id>`），读者只读主工作区和已发布索引。
- 收尾先在暂存分支提交，再在**一个数据库事务**里刷新全部派生表、推进事实状态、登记“已发布版本”（`users.workspace_head` = 提交 sha），事务提交后主工作区 `merge --ff-only`。
- 发布前任何失败：删暂存区即可，主工作区和索引从没被碰过，不再需要 `git reset --hard` + 重建索引这类补偿。
- 事务已提交但快进失败：保留分支；下次写入方开头发现 `workspace_head` 领先 HEAD 就补快进。读者发现两者不一致时，也可以不阻塞地抢写入锁补快进，抢不到就照常读。
  - 保留分支的标记要在**事务提交那一刻**就置上，快进成功后才撤。中间任何异常都会走 `finally` 删分支；主工作区还没追上时，分支是新提交唯一的引用，删了它，提交只靠 git 的悬空对象保留期（默认约两周）活着。
  - 比对 HEAD 和已发布版本要分三种情况：HEAD 落后（祖先）就快进；HEAD 领先（人工提交过）就不是故障，重新同步索引并登记新版本；两者分叉或登记的提交已不存在才需要人工处理。只判断“HEAD 是不是它的祖先”会把人工提交误判成故障，卡死后续所有写入。
  - 快进失败不必把整次运行记成失败（数据已经发布），但要在结果里写明“已保留分支”，别只记在轨迹事件里。
  - 若主工作区在落后状态下有与新提交**同路径冲突**的未提交改动，`merge --ff-only` 会拒绝：此时不要静默覆盖人工改动，更不要先在旧 HEAD 上提交（会造成真分叉），应当保留现场、把 git `stderr`（Python 的 `CalledProcessError.__str__` 默认不含 `stderr`，封装时要显式拼接）连同 `git stash -u` 恢复指引一起抛出来。
- 索引同步拆成 `plan`（解析文件、算向量这类慢且要调接口的步骤，不写库）和 `apply(conn, plan)`（纯 SQL，进调用方事务），这是“单事务发布”能成立的前提。
- 人工改文件也要走发布：写入方开头把工作树里的改动提交并同步索引，维持“工作树干净、HEAD == 已发布版本、索引 == HEAD”三条不变式。
- 所有会改工作区或派生表的入口（整理、reindex）共用同一把租户咨询锁。
- 网络盘上 git 的小坑：进程崩溃会留下 `index.lock`，持锁时清理超过 10 分钟的；提交后跑 `gc --auto`；暂存根目录 0700。

## 2. 执行环境锚点：开跑前记下“坐标”

在根 span 上记一份锚点（完整的放属性，摘要进索引行，列表和统计不用解压）：

| 类别 | 内容 | 用途 |
| --- | --- | --- |
| 工作区 | 已发布版本、实际 HEAD、是否一致、工作树是否干净 | 复现时 clone 到这个提交 |
| 库水位 | 库时钟 `as_of`、最大事实序号、当时“待处理”的集合、日志条数与最晚时间、用户状态计数 | 复现时把事实表复制到这个水位 |
| 代码与依赖 | 代码提交、是否有未提交改动、源码/提示词/技能摘要、最新迁移、Python 与依赖清单哈希、外部工具版本 | 判断“是不是同一版代码”，给出用旧提交复现的命令 |
| 配置 | 模型配置、受控词表文件哈希，影响行为的常量 | 同上 |
| 决策 | 自动判定的模式与理由、候选集合 | 复现时仍传原始入参让判定重跑，核对模式与理由是否漂移 |

要点：
- 水位用**一条 SQL** 读出，天然是同一快照；`as_of` 取库实时时钟 `clock_timestamp()`（在 `READ COMMITTED` 下若事务先执行了 `set_config`，`now()` 停在事务起点，间隙内其他连接刚提交的日志会出现 `created_at > now()` 而被复现漏掉）。
- 代码指纹进程内只算一次；`env_digest` 只对代码+依赖+配置求摘要，不含水位，同一版本的运行摘要相同，便于聚合。
- 写进日志的不是配置原文而是哈希，密钥类配置（env 文件）不进指纹。

## 3. 时钟注入：一切“现在”都从 `as_of` 来

模型会读“当前日期”，代码会算“近 14 天”“距上次重整 7 天”。这些不注入就无法复现。

- 给提示词里的“当前日期”、统计窗口 SQL（`created_at >= %(as_of)s - interval`，并加 `<= as_of` 上界）、模式判定函数统一传 `as_of`。
- 写库的时间戳（`dreamed_at`、`last_dream_at`）保持真实时间，不要被注入值污染。
- 待处理集合也按锚点水位截断（`msg_seq <= max_msg_seq`），开跑后新录入的不混进来。

## 4. 回放租户：在隔离环境里重建现场

每次重跑建一个全新的 `replay-*` 租户（多次重跑互不污染）：

1. 工作区：`git clone` 原工作区，reset 到锚点提交，去掉 remote。
2. 事实表：用建表账号（RLS 的 owner 维护策略）单事务跨租户复制——日志按 `as_of` 截断并重映射主键、事实行按序号截断并保留序号/批次/时间、当时待处理的恢复成待处理、用户计数与序号游标写回锚点值。
3. 派生表**不复制**，按文件重新 plan/apply；向量按 `content_hash` 复用原租户的，不重复调接口（顺带检验“派生表可由文件确定性重建”这一不变式）。
4. 以原入参重跑并注入 `as_of`；新轨迹带 `replay_of` / `replay_run`。
5. **副作用护栏**：工具打 `side_effect` 标签，`RunContext.replay=True` 时循环直接拦截并回灌提示。只给真正对外的工具打（发消息、调外部写接口）；读库、读写隔离工作区这类在回放租户里可安全重做的不打。
6. 对比报告：结构化字段逐项比（结果、路由、过滤条件、核验序号、命中页；整理的模式、归档集合、改动文件与逐文件内容差异、索引计数），自由文本只展示不比；另列水位核对、环境差异、N 次稳定性计数。
7. 清理：默认删回放租户（库行、工作区、暂存区），保留回放轨迹作证据；列表和统计默认排除回放轨迹。

LLM 输出本身有随机性，“复现”的目标不是逐字一致，而是**同一输入环境下结构化结果的分布**：重跑 N 次看稳定性计数，比单次对比更能说明问题（例如候选区兜底检索 2/2 一致、维度检索 1/2 一致，就提示路由提示词对这类问题不稳定）。

## 5. 轨迹保留与清理

- 轨迹是复现的证据，默认长期保留；临时租户（测试、回放）按租户 `purge`。
- 内容寻址的 blob 被多条轨迹共享，删轨迹后做**标记-清扫**：扫描剩余轨迹的资产引用与 `$ref`，只删无人引用**且超过宽限期**的 blob——落盘顺序是“先 blob 后轨迹文件”，宽限期避开并发写入的窗口。注意去重写入命中已有旧 blob 时要 `utime` 刷新 `mtime`，否则早已过宽限期的旧 blob 在被新轨迹重新引用但轨迹尚未落盘的瞬间可能被清扫掉。
- 月度索引用 JSONL 追加写时，重写要和追加持同一把文件锁，并且**原地重写**（同一 inode），否则等锁的追加者会写进被替换掉的旧文件。
- 删真实用户的轨迹应当需要显式确认（`--force`），临时租户前缀白名单之外一律拒绝。

## 6. 已知边界

- 检索读的是主工作区，如果工作树有未提交的人工改动，锚点会记 `git_clean=false`，复现只能拿到最近一次提交——所以人工改动要走 reindex 发布。复现报告要把这种情况作为警告放在开头，别让人拿“不一致”去怀疑模型。
- 复现建的临时租户要**先登记、再创建**：先把名字放进待清理列表再建库行与工作区，否则建到一半失败（克隆、复制数据出错）时 `finally` 不知道要删它，临时租户就残留下来。
- 网络盘上 git 可能卡住，所有 git 子进程都要设超时；锚点采集里的 git 检查失败只记“未知”，不能让在线请求失败。
- 原租户若已 `gc` 掉了锚点提交（未被任何分支引用且超过两周），工作区无法还原；正常发布路径上提交都在主分支历史里。
- 代码摘要不同的复现只能说明“新代码在旧环境上的表现”；要还原旧代码，用锚点里的提交开 worktree 跑同一个复现命令（工作树当时有未提交改动时只能近似）。
- 外部模型服务本身的版本漂移无法冻结，只能在报告里记模型名与指纹。
