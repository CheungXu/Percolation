# 双工作区界面：桌面聚焦伸缩 + 移动端卡片滑动

适用于"两种高频动作需要随时切换"的产品界面（例如：记录 / 询问、编辑 / 预览、输入 / 结果）。核心思路：**不平分，而是让当前在做的那一侧成为主工作区，另一侧退后但保持可见**。

参考实现：正式版 `code/web/`（拾记凝境，接真实后端）；离线原型 `alternatives/product-ui/nordic/`（假数据）。

---

## 一、设计要点

| 场景 | 做法 | 目的 |
| --- | --- | --- |
| 桌面 | 光标（焦点）所在一侧约 63%，另一侧约 37%；主侧纯白浮起，副侧浅灰、内容降透明度但可读 | 主次分明，又不丢另一侧的上下文 |
| 桌面 | `Tab` 在两侧输入框间切换；副侧输入框用 `Tab` 键帽替代发送按钮 | 键盘用户零鼠标切换，且提示自带 |
| 移动 | 两张卡片横向排列，非当前卡片缩小退到屏幕边缘，只露出约 32px 的竖排名称边签 | "切换工作区"的空间感，边签可点 |
| 移动 | 顶栏工作区名像相机模式条，随滑动进度平移、缩放、渐隐 | 空间位置与卡片位置一一对应 |
| 联动 | 一侧的动作在另一侧给出可见反馈（光点流入、实时亮起相关条目、边签计数） | 让两侧的因果关系一眼可感 |

## 二、实现手法

- **一个进度变量驱动所有过渡**：移动端在滚动容器的 `scroll` 事件里算出 `--p = scrollLeft / maxScroll`（0~1），卡片缩放、蒙层、边签透明度、顶栏平移全部写成 `calc(... var(--p))`，跟手且无需 JS 动画。
- **桌面伸缩用 `flex-grow` 过渡**：`.panel { flex: 1 1 0; transition: flex-grow .6s }`，主侧 `flex-grow: 1.7`。切换时不重建 DOM，只切换类名。
- **伸缩时内容流保持贴底**：宽度变化会让文字重排、高度改变；切换后用 `requestAnimationFrame` 在过渡期内持续把"原本贴底"的列表滚到底部。
- **只认文本框焦点**：`focusin` 只在 `textarea / input` 上切换主工作区；点按钮（如引用标签）不应触发，Chrome 点击按钮也会让按钮获得焦点。

## 三、踩坑清单

- **`scroll-snap` 按变换后的盒子计算停靠位置**：卡片加了 `transform: scale()` 后，吸附点会偏移（实测 390px 宽屏偏 20px）。解决：把 `scroll-snap-align` 挂在轨道两端**不做变换的占位元素**上（首个 `start`、末个 `end`），卡片本身不设吸附。
- **边签会随卡片一起缩小**：边签宽度要大于露出宽度（露出 32px 时边签做 48px，并用渐变向内过渡），否则缩放后露出区边缘会漏出底下内容。
- **切换时保持键盘不收起**：按钮上 `mousedown` 时 `preventDefault()`，防止输入框失焦；在 `click` 回调里**同步** `focus({ preventScroll: true })` 到另一侧输入框，iOS 才允许焦点转移且键盘不闪。`preventScroll` 防止聚焦时把横向轨道瞬间拽过去。
- **iOS 输入框字号 ≥ 16px**，否则聚焦时页面自动放大。
- **键盘弹起时的可视高度**：`<meta name="viewport" content="..., viewport-fit=cover, interactive-widget=resizes-content">` 只对安卓 Chrome 生效；iOS 需用 `visualViewport.resize` 把应用高度设为 `visualViewport.height`，并 `scrollTo(0, 0)` 抵消系统推页。
- **整页 `innerHTML` 重渲染会打断输入法**：边输入边联动（如实时亮起相关记录）时，只原地切换类名和文字，不要重渲染。
- **自定义属性默认不可过渡**：未用 `@property` 注册的 `--p` 改值会瞬变；桌面端改用类名切换 + 普通属性过渡，移动端本来就由滚动逐帧驱动，不需要过渡。
- **顶栏用 `justify-content: space-between` 时别再塞空容器**：给浮层加了一个空的 `div` 容器作为第三个弹性子项，右侧按钮被挤到正中，移动端还被工作区标题挡住点不到。浮层容器设 `display: contents`（子元素本来就是绝对 / 固定定位，不需要它占位）。

## 四、接真实后端后的做法

原型阶段可以整页重渲染；接上异步接口后，结果随时可能在用户打字时回来，需要换一套渲染方式：

- **外壳只挂载一次，之后按区域局部重绘**（记录流、问答流、浮层各一个 `paint` 函数）。两个主输入框永远不重建，正在组字的输入法不会被打断。
- **重绘区域里的输入框**（如追问的「补一句」）在重绘前记下内容和光标，重绘后恢复。
- **乐观插入**：记一句时先插一条「发送中」条目并立即放动画，成功后换成服务端序号；失败标红并给重试，原文不丢。
- **慢请求的等待态写成进度叙事**：询问可能要 5–20 秒，「思考中」文案按耗时切换（翻看你的记录 → 核对原话 → 组织回答 → 还在想），只更新文字节点，不重绘整条线程。
- **边输入边联动的召回要便宜**：每次停顿都会触发，只做词面匹配不调模型。中文按二字组切词时，跨词边界会切出「四见」「总要」这类不存在的词，命中门槛要按「在库里确实出现过的词」计数，否则真正相关、只命中一个词的条目会被漏掉。新请求用 `AbortController` 中止旧请求，并核对返回时输入框内容没变。
- **依据定位要能翻页**：被引用的原话可能比已加载的更早，点依据时先向前翻页直到覆盖，再滚动并高亮。
